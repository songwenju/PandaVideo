# Spec Review Workflow

把“Agent 读出来、问出来，人在 Review 处回答”落实为可追溯的交付流程。
默认用中文编写文档，沿用项目术语和已有文档约定。

## 核心规则

- 先读取 PRD、Figma、多语言、埋点及相关知识库，再提问。可以从材料确定的内容直接写入文档，附来源。
- Spec 只写“要什么”：用户行为、业务规则、范围、状态和验收标准。把架构、接口实现、技术选型放入 Tech Solution。
- 材料中读不出的默认预期，由 Agent 在对应 Review 提问，人回答后回写文档；不得把推断写成已确认事实。
- 人工 Review 共四道：Line Review、Spec Review、Tech Review、自测 / QA 测。Spec 与 Tech Review 各有 Clarify 回环；QA 有 Fix 回环。
- 先交付可审阅的文档、证据和明确问题，再请求 Review；不要只提交空泛计划或“是否继续”。
- 尊重用户已给出的授权、确认与任务范围。同一版本同一决策不重复求确认；用户指定只做某阶段时，完成该阶段即可。
- 不把此流程当作所有小修改的强制入口，不擅自扩展为发布、推送或对外发送消息的授权。

## 启动与产物

1. 明确目标、当前阶段、请求范围和已有 Review 结论。已有成果可以复用，不强制从 Step 0 重来。
2. 定位并读取相关文件与来源。记录无法访问的素材；使用可用信息继续工作，不声称已读取缺失素材。
3. 按项目约定选择本次需求文档目录；无约定时使用 `docs/specs/<feature>/`。不要覆盖无关需求。
4. 按需复制 [文档模板](assets/document-templates.md) 中对应部分，删除无关占位内容。
5. 用需求编号串联 Spec、方案、任务和测试证据。用问题编号串联问题、回答及修改位置。

建议产物：

| 文件 | 用途 |
| --- | --- |
| `inputs.md` | 素材清单、知识库来源、输入准备及 Line Review |
| `spec.md` | 需求行为及可验证验收标准 |
| `tech-solution.md` | 各端技术设计及系统协作 |
| `tasks.md` | 可选的实施任务拆分 |
| `review-log.md` | 四道人工 Review 的问题、回答、结论 |
| `verification.md` | Agent 自测、QA 结果、Fix 和回归证据 |
| `release.md` | 发布准备、执行结果与回滚信息 |

只创建当前阶段实际需要的文件。未知项标记为“待澄清”，不要伪造完整度。

## Step 0 — 环境 / 需求准备

读取 PRD、Figma、多语言文案、埋点方案。读取业务知识 KB，识别业务术语、目标用户、上下游及历史约束。

检查代码入口、工作区约定、构建和测试方式、权限及运行环境。把素材版本、来源位置、缺失输入和已有授权写入 `inputs.md`。

提交 **Line Review**，对应角色 PM、UX、DA。请人回答输入一致性问题，例如设计和 PRD 是否冲突、文案是否完整、埋点口径是否确定。
只有实际获得的人工结论才记录为通过。先解决影响需求理解的输入问题，再将结论纳入 Step 1。

## Step 1 — PRD 理解和拆分

把材料转换为 `spec.md`：

- 目标、用户场景、范围与非目标。
- 主流程及异常、空态、加载、失败、恢复等可见行为。
- 业务规则、文案、多语言与埋点要求。
- 编号需求及验收标准；确保 QA 可以据此判断通过或失败。
- 来源、明确假设及尚未确认的默认预期。

提交 **Spec Review**，对应角色 PM、RD、QA。
对材料无法决定的业务语义、边界和验收口径，提出具体问题及影响。

**Clarify 回环**：收集回答 → 更新 Spec 与问题记录 → 重审受影响内容。
未通过的需求项回到本阶段；已确认且不受影响的条目不重复审阅。

## Step 2 — Tech Design（C&S）

读取相关各端 Coding KB 与现有实现。图中的 C&S 缩写沿用原文；项目未定义时不要擅自解释其全称。

生成 `tech-solution.md`，覆盖实际相关的客户端与服务端：

- Spec 编号到实现模块、边界和数据流的映射。
- 接口 / 数据契约、状态管理、异常处理和兼容性。
- 各端共用与特有设计、多语言和埋点接入方式。
- 关键技术取舍、依赖、性能及验证策略。
- 迁移、上线与回滚考虑；不适用时注明原因。

提交 **Tech Review**，对应角色 RD。
针对材料无法确定的接口契约、架构边界、技术约束及取舍提问。

**Clarify 回环**：收集回答 → 更新方案 → 重审受影响内容。
技术澄清若改变用户行为或验收条件，同时回写 Spec 并触发相关 Spec 重审。

## Step 3 — Impl Task 拆分（可选）

需求较大、存在依赖或需要多人协作时生成 `tasks.md`；简单需求跳过并记录原因。

每项任务写明关联需求、实施范围、前置依赖、完成条件和验证方法。
按依赖顺序排列，区分可并行任务，不把依赖未完成的任务标为可执行。

## Step 4 — Code Impl

按已确认的 Spec 与技术方案，在用户授权范围内实施。
遵循各端 Coding KB 和仓库规范，及时执行相应编译、测试或静态检查。

新发现的产品问题回到 Spec Clarify；技术问题回到 Tech Clarify。
可独立推进且不受待答问题影响的工作继续完成。
实现结果、任务状态及文档必须一致，不悄悄变更已确认的验收标准。

## Step 5 — Agent 自测

读取适用的 Testing AGI KB。根据 Spec 验收标准设计并执行测试，覆盖主流程、边界、异常与实际相关端。

将环境、版本、命令或步骤、预期、实际结果与证据位置写入 `verification.md`。
区分通过、失败、阻塞、未执行；编译通过不等于业务验收通过。

能自行修复的缺陷先修复并回归，再交付 QA；不能复现的问题记录条件与证据缺口。
此步骤为 Agent 自动验证，不替代 Step 6 的人工 Review。

## Step 6 — 自测 / QA 测 + Fix

提交第四道人工 Review，对应角色 RD、QA。
提供可运行产物、测试步骤、Agent 自测结果及待确认的体验问题。

**Fix 回环**：记录反馈 → 关联需求 → 修复 → 验证原问题及受影响流程 → 更新证据 → 请求相关项复测。
反馈改变需求时，回到 Spec / Tech 对应阶段。

仅将有实际人工反馈的条目标为人工验收通过；Agent 自测通过不能代填 QA 结论。
无法获得人工反馈时，完成准备工作并准确标记“待人工 Review”。

## Step 7 — 发布

根据项目发布规范，准备版本信息、变更说明、验收证据、已知限制及回滚方案。
检查本次范围内的需求与缺陷状态；未解决的事项需要明确处理结论。

发布动作必须在用户实际授权范围内执行。尚无发布授权时，交付可审阅的发布准备材料。
记录实际执行版本、时间和验证结果，未执行时标为“待发布”。

## Review 提问与记录

每次集中提交少量高影响问题。每个问题包括：

1. 所属 Review、问题编号及相关需求。
2. 已读取的来源和其中已能确定的内容。
3. 无法确定的具体预期、冲突或缺口。
4. 可选答案及推荐理由（有合理选项时）。
5. 回答会影响的行为、方案、测试或交付。

不要提问可通过读取现有材料解决的问题，不让人代替 Agent 分析代码。
可逆的常规工程选择由 Agent 决定并记录；影响业务行为、核心契约或显著取舍的问题交给对应 Review。

Review 记录保留版本、问题、答复、状态与更新位置。
区分“待答”“已答待更新”“已更新待复审”“通过”；以真实反馈更新状态。
用户已授权跳过某道 Review 时，记录跳过范围和依据，不伪记为人工通过。
